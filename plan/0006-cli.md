# 0006 — Command-line interface

- **Status:** Draft (principles decided — ADR-0017; each command is specified in the feature plan of its milestone)
- **Related ADRs:** 0004, 0007, 0008, 0010, 0017, 0018, 0024, 0026, 0027, 0033, 0035–0042

The executable is **`hio`** (ADR-0018): `hio chester app flash …` instead of `hardwario chester app flash …`.

## Purpose

A headless binary (`app/cli`) on the same backend as the GUI:

- **Drop-in replacement for the `hardwario` command of py-hardwario** for developers, production
  and CI scripts.
- **Headless test harness**: hardware features (RTT, flashing, BLE) are usable and testable from
  the CLI before the GUI exists.
- **MCP over stdio** (`... mcp`, ADR-0008).

Because the backend is UI-independent (ADR-0004), the CLI only parses arguments, calls backend
APIs and formats results — no logic of its own.

## Principles

1. **py-hardwario compatible** command tree and option names, so existing scripts keep working
   with at most a changed executable name.
2. **Grows with each milestone**: skeleton in M0; every backend feature plan also specifies and
   implements its CLI command(s) and tests.
3. **CLI11** (pinned via CPM) for argument parsing, nested subcommands, validation, help.
4. **Human output by default** (colors when a TTY, progress bars for long operations),
   **`--json`** for machine-readable results. Errors are printed from `hio::Error`:
   message, likely cause, suggested fix; with `--json` as a structured object.
5. **Stable exit codes** per error category (documented; part of the public contract).
6. Ctrl+C cancels the running operation cleanly (stop token), never leaves the probe locked.
7. Non-interactive by default when stdin is not a TTY (no prompts; `--yes` to confirm
   destructive operations).
8. **English only** (ADR-0027): the CLI never loads a translation, so output is stable for scripts and support.

Common options as in py-hardwario: `-n/--jlink-sn`, `--jlink-speed`, `--halt`; console options
`--latency`, `--history-file`, `--console-file`, `--auto-reconnect`, and (new, M1) `--linger S` for the
non-interactive / `--json` console (output collected S seconds after the end of stdin; default 1.0, 0–60).

BLE commands (M5, plan 0011) pick the device with `-a/--address ID` (MAC address, or the CoreBluetooth UUID on
macOS) or `--name N` (a case-insensitive part of the advertised name; exactly one device found by a 5 s scan
must match). `ble scan` lists the devices of `--profile` (default `chester`; a device belongs to a profile by its
advertised name only, ADR-0142), `--all` every device. A connect may take up to 30 s: failed attempts are retried within that time,
with growing delays while BlueZ is still busy with an earlier attempt (HIL H3/H6/H8); an unbonded device waits
up to 60 s for the passkey. `ble pair` asks the operating system to pair (Linux, Windows); on macOS it is
`ble.pairing_not_supported` (macOS pairs on the first connect). All Bluetooth work runs on one BLE thread
(an owned `std::jthread`, ADR-0141).

## Exit codes (ADR-0024, public contract)

| Code | Category | Meaning |
|---|---|---|
| 0 | — | success |
| 1 | internal | bug / unexpected error |
| 2 | usage | invalid arguments or options; `ble pair` on macOS (`ble.pairing_not_supported`) |
| 3 | io | file not found / not readable / not writable, settings |
| 4 | dependency | J-Link library or nRF Util missing / incompatible, or Bluetooth adapter (missing, off, permission, system service), or no pairing agent on Linux (`ble.no_pairing_agent`, only when BlueZ cancels the pairing at once) |
| 5 | probe | J-Link probe not found / busy / firmware problem; a BLE device used by another program (`ble.in_use_by_other_process`) |
| 6 | target | device not responding, wrong MCU family, low voltage, or BLE device (not found, no connection within 30 s, no console service, not paired, pairing failed, write failed, connection lost) |
| 7 | firmware | invalid image, verify failed, catalog id unknown |
| 8 | network | download / catalog API failure |
| 9 | timeout | operation timed out |
| 130 | cancelled | Ctrl+C / SIGTERM |

## `--json` output (ADR-0026)

One envelope object per line on stdout: `{"schema":1,"ok":true,"data":{…}}` or
`{"schema":1,"ok":false,"error":{"code","category","message","cause","suggestion","detail","wizard"}}`.
Streaming commands emit NDJSON envelopes. Logs never go to stdout.
